# Design Decisions Log — Phase 0.1

Entry types:

- **Confirmed (C-xx):** decisions from the original brief. Each entry records
  its status after review.
- **Refinements (R-xx):** decisions made during review. Phase 0 entries keep
  their IDs. Superseded entries are marked, not deleted.
- **Unresolved (U-xx):** open questions, classified in Phase 0.1 as
  **BLOCKER**, **DEFERRED** or **OPTIONAL** (§3).

Section references (§) point to `architecture.md`. Risk IDs point to
`technical-risks.md`.

## 4. Implementation-language comparison

The selection (OCaml) is recorded in U-03 and section 6 below. This section is unchanged
in substance from Phase 0. The Phase 0.1 changes
make cyclic run-time values (closures in `Ref` cells) and persistent
registries certain requirements, and add the trusted primitive table and
deterministic counters. None of these changes the ranking.

| Criterion | Rust | OCaml | Haskell |
|---|---|---|---|
| ADTs + exhaustive matching | Excellent | Excellent | Excellent |
| Cyclic interpreter values | Hard: needs arena + collector | Easy: GC | Easy: GC; laziness can leak space |
| Persistent maps | crates | stdlib | `containers` |
| Mutable compiler state | natural | natural | monad stacks |
| Refactoring velocity | moderate | high | high when pure, lower with effects |
| Compile times | slow-ish | fast | slow |
| Testing | `cargo test`, `insta`, `proptest` | `dune`, expect tests, `qcheck` | `tasty`, QuickCheck |
| AI-assistance quality | strongest | good, thinner corpus | weaker |
| Language-implementation precedent | rustc, Boa, Rhai | Rocq, Flow, Hack, Haxe, early rustc | GHC, Agda, Idris 1, PureScript, Elm |
| Long-term performance / VM | best | good | good, harder to tune |
| Distribution | best | good | moderate |
| Counters and non-local exits in the interpreter | `Result` unwinding | exceptions / OCaml 5 effects | exceptions / `ExceptT` |

- **OCaml** suits the semantic tranches (T2–T10).
- **Rust** suits long-term tooling, distribution and AI productivity, at the
  cost of a custom heap for interpreter values.
- **Haskell** suits the trusted checker and property tests. It is weakest
  for the stateful expander.

**Decision procedure (U-03, owner).** Weight the criteria.

- Velocity and cyclic values dominate → OCaml.
- Tooling, distribution and AI assistance dominate → Rust.
- Haskell only if the owner is already fluent in it.

An optional, throwaway one-day spike (T2a-sized core checker in two
candidates) would give direct evidence. It requires a separate
instruction.

## 5. Explicitly rejected alternatives

| Alternative | Why rejected |
|---|---|
| Generalized parsing of composed grammars | Conflict rejection at activation is required; grammar ambiguity is undecidable in general (per-input ambiguity is detectable, but too late for C6). |
| PEG ordered choice across extensions | Order-dependent silent resolution. |
| Longest match + priority + choice nodes | A valid, deterministic design (Lean), but it defers ties to elaboration; C6 requires rejection. |
| Declaration-dependent tokenization; splitting operator runs by declared operators | Declarations would change the meaning of existing code. |
| Whole-language reader replacement | Global grammar replacement is outside the goal. |
| Checkers bypassing the core | Removes G1–G6. |
| Numeric precedence | Does not compose. |
| Rhombus-style non-transitive precedence | Coherent, but needs more declarations and loses ordered arrays as the user-facing form (§2.5.7). |
| First-class grammar values; built-in combinator framework; public typed IR | Redundant with declarations + macros; enlarges the public surface (§8.4). |
| Macro-granted access to private types (annotation scheme) | Forgeable by an untrusted elaborator (S-04). |
| Precedence override by edge deletion | Non-monotone; hard to specify with imports. |

## 6. T1 implementation record

T1 implements the lexer and token-tree reader (`architecture.md` §2.1, §8.1
components `lexer` and `reader`) and the `lexdump` diagnostic CLI. Nothing
in this section changes a frozen section. Section 6.2 records how T1 reads the
frozen text where it leaves a choice open; section 6.3 records diagnostic codes
added for precision.

### 6.1 Language, toolchain and memory (U-03, U-16)

- **Implementation language:** OCaml (owner decision).
- **Toolchain:** OCaml 5.5.2 (`ocaml-base-compiler.5.5.2`), Dune, opam. The
  switch is repository-local (`_opam/`, created by
  `opam switch create . ocaml-base-compiler.5.5.2`). `dune-project`
  constrains `ocaml >= 5.5.2 & < 5.6`.
- **Dependencies:** none beyond the compiler, its standard library and Dune.
  Tests use a stdlib-only harness and Dune cram tests. The test-only oracles
  also use `str`, which ships with the compiler.
- **Memory:** run-time values will initially use the OCaml garbage
  collector. This relies on the host runtime. Memory safety of the
  implemented language is **unverified**. The OCaml compiler and runtime are
  implicitly trusted, as any host would be.

### 6.2 Interpretations of the frozen lexical contract

| ID | Question left open by §2.1 | T1 reading |
|---|---|---|
| I-01 | Are control characters allowed inside strings, comments and raw regions? | Yes. The "outside strings, comments and raw regions" qualifier is read as applying to control characters too. Strings still reject raw LF and CR (I-03). **Ratified as R-47 (T1.1).** |
| I-02 | Is a lone CR a line end? | No. "Line ends are LF or CRLF": a lone CR is whitespace, does not set `newline_before`, and does not start a new line for positions. |
| I-03 | "No raw newlines" in strings | Raw LF and raw CR inside a string are errors (CR is rejected so that CRLF cannot enter a string). **Superseded by I-17 / R-48 (T1.1).** |
| I-04 | Does `space_before` / `newline_before` count comments? | Both are computed over all trivia (whitespace and comments) immediately before the token; `newline_before` holds when that trivia contains an LF, including inside a long comment. |
| I-05 | `--[` not followed by `=ⁿ[` | A line comment. |
| I-06 | `0x` with no hex digit; `0X` | `0x` is `0` with suffix `x` (the hex rule needs one character of `[0-9A-Fa-f_]`); `0x_` is a hex literal as the regex allows; `0X…` is never hex. |
| I-07 | Meaning of `digits` in floats | `[0-9][0-9_]*`, the same as decimal integers. |
| I-08 | `"…"` directly followed by an identifier | Two tokens; "suffix not allowed" means a string never absorbs one. No error. |
| I-09 | Shape of `\u{hex}` | 1–6 hex digits, the value must be a Unicode scalar value (≤ U+10FFFF, not a surrogate). Any other escape is an error. |
| I-10 | Error reporting policy | The whole input is validated as UTF-8 first; lexing then stops at the first error. Numeric values are not range-checked by the lexer. |
| I-11 | Which tokens are operands for the lint? | `ident`, `raw-ident`, `int`, `float`, `string`, `raw-region` and closing delimiters. The lint fires for line and long comments that start exactly at the end of an operand. |
| I-12 | "Both spans" for each delimiter error | Mismatch: close span, plus the open span as a note. Unclosed at end: the innermost unclosed open, plus the end-of-input span as a note. A stray close has only one delimiter, so it reports one span. The first error in source order is reported. |
| I-13 | UTF-8 byte order mark | Not special: a leading BOM is `E-LEX-CHAR`. |
| I-14 | Span and position conventions | Spans are half-open byte ranges `[start, stop)`. Lines and columns are 1-based; columns count bytes. |
| I-15 | Token trees and `env` (§2.6.1) | T1 trees carry no `env` field; every T1 tree is user source (`Source`). The field arrives with syntax objects in T4. **Superseded by I-18 (T1.1):** this contradicted U-07, which assigns the field to T1. |
| I-16 | Trivia | Each token owns the whitespace and comments before it; `eof` owns trailing trivia. Concatenation reproduces the source (LEX-13). |
| I-17 (T1.1) | Line ends inside strings | LF is `E-LEX-STRING` at the LF; CRLF is `E-LEX-STRING` over both bytes; a lone CR is an ordinary string byte (R-48). Escapes `\r` and `\n` are unaffected. A backslash before a raw CR or LF is `E-LEX-ESCAPE`. |
| I-18 (T1.1) | Grammar-environment stamp | `Grammar_env.t` is an opaque type, separate from file identity (`Span.file`). `Reader.group` has `env` and `span` fields, and `Reader.t` has a root `env`, matching §2.6.1 `Group(delim, children, env, span)` and the root env of `TokenTree`. T1 has one value, `Grammar_env.source`, which records the tree's origin (user source). It does **not** show that later environments are tracked correctly. T4/T5 add stamp values and re-stamping behind the same interface. |
| I-19 (T1.1) | `Reader.read` input contract | Exactly one `Eof`, in the last position. `[\|eof\|]` (empty source) is valid. Violations return `Invalid_input (Missing_eof \| Eof_not_last {index})` before any grouping, instead of raising or dropping tokens. Delimiter errors are `Unbalanced diagnostic`. |
| I-20 (T1.1) | Dump formats `tokens/2`, `trees/2` | Both escape C1 controls, bidirectional controls, U+2028/2029 and U+FEFF as `\u{XXXX}`, in addition to ASCII control bytes. `trees/2` shows `env=` on the header and on every group line. Indentation is capped at 32 levels; deeper lines carry `depth=N`. This removes the indentation term that was quadratic in depth. It does not make output depend on token count alone: the size bound and costs are stated in `src/dump.mli`. |
| I-21 (T1.1) | Diagnostic rendering | File names and messages pass through the same escaping (without quoting). |

### 6.3 Diagnostic codes added in T1

§2.1 names `E-LEX-UTF8`, `E-LEX-CHAR`, `E-LEX-COMMENT`, `E-LEX-RAW`,
`E-LEX-UNBALANCED` and `W-LEX-COMMENT-AFTER-OPERAND`. T1 adds three codes for
inputs that §2.1 already rejects, without accepting or rejecting anything new:

| Code | Raised for |
|---|---|
| `E-LEX-STRING` | unterminated string; a raw line end inside a string (LF, or CRLF reported over both bytes). A lone CR is an ordinary string byte (R-48, I-17). |
| `E-LEX-ESCAPE` | escape outside the §2.1.3 list; malformed or out-of-range `\u{…}` |
| `E-LEX-RAW-IDENT` | a backtick not followed by an identifier and a closing backtick (otherwise this would be `E-LEX-CHAR` on the backtick) |

### 6.4 LEX conformance mapping

Test targets:

- `dune test`: `test/unit/test_front` (`suite_lexer`, `suite_reader`,
  `suite_oracle`, `suite_generated`), `test/unit/test_stack`, and the CLI
  cram test `test/cli.t/run.t`. Both unit executables run with

  in effect.
- `dune build @stress`: `test/stress/stress.ml` contains exhaustive UTF-8
  checks, 300k numeric-literal cases, work-scaling checks (each measurement
  must lex and read successfully), and 32,000,000-byte and 10M-deep inputs.
  It is not part of `dune test`.

oracles independent of the lexer: the stdlib UTF-8 decoder, `Str` regular
expressions transcribed from §2.1.3, the input bytes, and the generator's
tree. The operator-run model is a simplified restatement of §2.1.4 by the
same author, so it can share a misreading.
