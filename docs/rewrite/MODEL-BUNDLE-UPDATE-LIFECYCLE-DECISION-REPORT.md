# ModelBundle update lifecycle: provisional architecture decision

**Status:** research proposal for maintainer review, 13 September 2026. **Repository baseline:** `a54c559ccb821438b6ec3b09825893e49d3ab4e2`. No update command, legal-event model, source monitor, or accepted lineage protocol is implemented here. The companion [change-impact specification](MODEL-BUNDLE-CHANGE-IMPACT-PROVISIONAL-SPEC.md) is likewise provisional.

## Executive recommendation

Implement an **external `ModelBundleChangeSet-v1` and offline `yuho-model-bundle diff`** as the next bounded milestone, subject to the gates below. Compare two independently validated [ModelBundle-v1](MODEL-BUNDLE-V1.md) cores by exact digest and closed structure; emit a content-addressed mechanical report. Leave both cores and their existing digests untouched. An ordered comparison is **not** a claim that the second bundle legally supersedes, corrects, amends, or should replace the first. A separate future, supplied lineage/deployment assertion may make such a claim under an explicit trust policy. No new KernelInput/KernelResult variant is justified.

This adds a capability the current validator lacks: reproducible evidence of *which registered bytes and model records differ* between two exact bundles, and a conservative list of IDs meriting review. It does not establish legal change, semantic equivalence, source authenticity, currency, or legal correctness. A new bundle digest requires a new review assertion for that digest; a diff never renews one. Preserve old bundles for offline replay and rollback by exact digest.

## Events that must not be collapsed

| Event | What an offline comparison can establish | What remains supplied or external |
| --- | --- | --- |
| Retrieval change | Nothing about a live locator; at most compare two stored locator strings or acquisition records. | That the same URL returned different bytes at specified times. |
| Artifact change | Raw digests/lengths/roles differ; added, removed and retained digest identities. | Why bytes changed or whether they are official. |
| Extraction change | Child text digest or `derived_from` recipe/edges differ. | Extraction fidelity and whether parent bytes represent the claimed legal text. |
| Manifestation change | A local manifestation record was added, removed or modified. | Whether it is a replacement publication or the same expression. |
| Expression change | A local expression grouping or metadata differs. | Version identity and legal effect. |
| Work change | A local work grouping differs. | Whether two legal instruments are truly identical, related or distinct. |
| Mapping change | A semantic ID's source/artifact/role/span tuple differs, including span-only changes. | Whether either passage faithfully supports the rule. |
| Model change | Whole executable artifact digest differs; exact JSON fields may differ. | Semantic equivalence, a lawful amendment, or which case facts should govern. |
| Scope change | Exact positive IDs, source/expression inventories, exclusions or limitations differ. | Completeness for a legal purpose. |
| Metadata change | Descriptive publisher, locator, jurisdiction and date values differ. | Their truth or legal applicability. |
| Review change | Detached records were added, removed or changed; exact-digest applicability. | Authentication, qualification, revocation and renewed legal review. |
| Legal event | **Not derivable from the comparison.** | Enactment, commencement, amendment, repeal, correction, judgment or operative effect requires identified official material and review. |
| Deployment change / rollback | **Not derivable from the bundles.** | A consumer's recorded choice of a new or earlier exact digest and its policy rationale. |

## Immutable lifecycle, identity and lineage alternatives

1. **Acquire outside the validator.** A future acquisition tool may record a locator, retrieval UTC time, response metadata/redirect chain, and exact bytes. A changed response digest creates a new artifact and candidate manifestation; a human classifies its relationship to prior work/expression and any legal event. No polling or fetch occurs in `validate` or `diff`.
2. **Build a fresh closed core.** Never edit an old content-addressed package in place. Its existing directory can physically mutate, so storage policy should make old cores read-only or snapshot them; every use must verify the expected digest and bytes. Cache key: `(bundle_digest, validation_profile, validator_version)`, with digest recheck on load. Reject a mutated package as a match for its old digest. Keep old artifacts addressable; deletion is an availability failure, not supersession.
3. **Compare two exact cores.** Directory names and modification times do not matter. Same canonical core bytes mean same digest even in another directory. Core changes get a new digest. The existing local `model_id` may be retained as a descriptive family label but has no cross-bundle uniqueness guarantee. A human release version may be recorded in a separate catalog or future core profile; it never replaces the digest. Two different `model_id` values permit mechanical comparison but make the claimed model relationship unknown.
4. **Review and deploy separately.** Detached review files may change without changing the core digest. Old reviews apply only to their exact digest. A new assertion must name the new digest, exact purpose and positive coverage; it may cite the old digest and a change-set digest as *context*, but neither context transfers coverage. Deployment/rollback selects an exact available digest under external policy; both are separate operational events.

| Alternative | Assessment |
| --- | --- |
| A. Add predecessor fields to `ModelBundle-v1` | Would change accepted core bytes/digests, create self-referential update pressure and confuse technical comparison with asserted succession. Reject. |
| B. External `ModelBundleChangeSet-v1` | Reuses independently valid immutable cores, leaves all accepted hashes untouched, enables deterministic offline comparison and focused review. **Recommend.** An ordered old/new pair records comparison direction, not legal supersession. |
| C. Mutable source/model registry | Useful only as an untrusted discovery index. In-place updates erase reproducible old identity and complicate rollback. Reject as identity. |
| D. Git history alone | Repository commits can locate development states but need not include source acquisition, deployed package or external reviews; Git ancestry is not legal lineage. Reject as sole relationship. |
| E. Full legal-amendment engine | Requires reviewed amendment instructions, consolidation and point-in-time doctrine. Outside this milestone. |

One change set compares **exactly one old and one new digest**. Several records may share an old digest (branching), a new digest (candidate merge), or compare unrelated bundles; they do not automatically form a predecessor graph. A directed comparison cycle is not itself invalid because comparisons are not lineage. A *later supplied lineage assertion* should name exact digests, distinguish revision/correction/merge/rollback claims, reject cycles in its own claimed-ancestry graph, and never declare legal supersession merely from graph shape. For v1, keep those assertions outside the computed report. Deleted historical bundles make a comparison unavailable, not a reason to fabricate a predecessor. Rollback is selecting an old digest, not mutating history.

## Impact, reviews, time and threats

The [provisional specification](MODEL-BUNDLE-CHANGE-IMPACT-PROVISIONAL-SPEC.md) defines exact record keys and conservative ID categories. Artifacts compare by digest; a removed digest plus added digest is **not** automatically a modified manifestation. Equal local source/expression/work IDs permit a structural comparison of supplied labels only. A claimed rename or successor needs a separate assertion. Mappings compare by exact tuples and spans, with ambiguous many-to-many pairing reported as `unknown_relationship`. `semanticIds` supplies ID inventories, but current validators do not export a complete versioned dependency graph or stable per-ID semantic fingerprint. A changed executable request therefore makes downstream impact on retained IDs **unknown**; no fixture-output equality or same ID can narrow that claim. A later complete, fragment-versioned reference extractor could compute bounded reverse reachability, with tests for definitions, inherited requirements, exceptions, presumption conditions, penalty guards and term containment. Until then, direct structural differences only are normative.

Review invalidation is exact: when `old_digest != new_digest`, **every** old review is non-applicable to the new core, even if the only core change is descriptive metadata; no purpose or covered ID transfers. When digests are equal, the core is the same and a matching old assertion remains applicable to that digest even if a directory omits a copy of its review file. A review-only change alters assertion inventory, not the core digest. The current validator reports applicable, stale and partial review IDs and an optional purpose-policy result; the proposed comparison may additionally inspect outcomes and report missing or conflicting unsigned assertions. Neither has an authenticated revocation/expiry mechanism, so it must not call an assertion revoked or trusted. Exclusions are not positive review coverage.

All currently stored dates—publication, decision, revision, commencement, effective bounds, retrieval, supersession and scope point-in-time—are calendar-checked descriptive assertions, with a few local chronology checks. Review timestamps are parsed UTC but unauthenticated; no bundle-creation or deployment timestamp exists in the core. A future acquisition record can supply retrieval time; an external deployment log can supply selection time. The kernel's reference date is a case evaluation parameter. A retroactive change, future commencement or superseded consolidation cannot be resolved by date sorting here. The update layer reports changed date fields without selecting the bundle that legally governs an evaluation date.

| Threat or failure | Recommended treatment |
| --- | --- |
| Old directory mutated, predecessor bytes substituted, deleted archive, enormous diff | Revalidate exact old/new digests and package types from a stable snapshot; reject mismatch/unavailable input and enforce output/count limits. No partial impact report. A one-time `validate` alone cannot rule out a concurrent filesystem race. |
| False `supersedes`, amendment or correction claim; reused semantic ID; inferred rename | Do not emit as computed fact. Report same-ID structural comparison and `unknown_relationship`; require separate, source-linked human assertion and policy. |
| Lineage cycles, two successors or claimed merge | Comparison edges do not assert lineage. Future lineage-assertion graph must reject cycles and report branches/merges without choosing a winner. |
| New URL bytes, hidden extraction-tool change, source/model updates in conflict | Report exact locator, artifact, derivation, mapping and model differences independently. Never mutate an old blob or classify a legal event automatically. |
| Old review copied to new directory; diff presented as approval | Report old subject as stale; require new exact-digest assertion. Keep `review_authentication: none` and prohibit certification language. |
| Rollback to outdated/vulnerable model, clock manipulation, unauthenticated review revocation | Record selected digest and asserted times externally; deployment/trust/revocation policy decides use. Offline diff neither blesses rollback nor authenticates timestamps. |

## Compatibility, implementation and reversal gates

**Preserved:** accepted `ModelBundle-v1` manifest, SHA-256 domains, detached review schema, all seven kernel request/result bytes, Canonical IR v1.2, Python parser/CLI/LSP, fixture bytes and current `validate` semantics. **Separate extension:** a new change-set schema/result protocol, CLI `diff`, synthetic comparison fixtures and bounded properties. **Adapter-only:** optional import of AKN/ELI/SSO identifiers, legacy AST diff or acquisition logs with explicit loss reports. **Deferred:** online monitoring, verified publisher identity, amendment consolidation, dependency closure, legal applicability, signing, review revocation and deployment selection. **Prohibited:** automatic legal-event or review-transfer claims.

Implementation gates: independently validate and pin both complete directories before reading comparison records; define stable canonical ordering and domain-separated change-set digest; test every object class, ambiguous mapping alignment, Unicode/CRLF, changed model with same IDs, review-only changes, source-only changes, stale/partial/conflicting reviews, invalid inputs, symlinks, resource limits, deterministic bytes and clean offline replay. Do not reuse Python AST diff heuristics. The proposed result must visibly separate mechanical facts from unknown legal relationships and refuse truncation. Reversal gate: if a useful bounded report needs complete cross-fragment dependency closure or globally stable work IDs that v1 cannot supply, ship a narrower direct-structure report or first version a compiler-owned dependency/identity artifact; do not silently claim semantic impact. If current package validation cannot operate on an immutable snapshot under the intended hostile filesystem model, defer high-trust use until snapshot/descriptor-relative traversal is designed.

**Maintainer decisions still open, with recommendations:** approve B and one `diff` command (**yes**); treat `model_id` as a descriptive family label, not identity (**yes**); allow comparison of different model IDs but mark relationship unknown (**yes**); exclude asserted supersession/rename/merge and release labels from computed v1 (**yes**); keep review changes outside the digest and require fresh assertions for every new core digest (**yes**); initially report direct ID changes and conservative unknown downstream impact rather than incomplete dependency propagation (**yes**); keep acquisition, deployment and legal applicability outside the tool (**yes**). Jurisdiction-specific mapping of a Singapore amendment, revised edition, renumbering or commencement to a new bundle requires qualified legal review, not a maintainer-only default.
