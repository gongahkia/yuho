# Legal-source registration and model-scope boundary: provisional decision

**Status:** historical architecture research, 13 September 2026; its recommended package boundary was accepted for the separate [ModelBundle-v1 specification](MODEL-BUNDLE-V1.md). **Research baseline:** `d2c69981eda797367e2222089ab2028ce63a179a`. This document itself is not the production schema and specifies no legal doctrine. Read the companion [threat model](MODEL-SCOPE-AND-PROVENANCE-THREAT-MODEL.md) before treating a bundle as evidence of anything beyond the checks stated here.

The accepted v1 pins the existing explicit sorted-JSON encoder as `yuho.sorted-json/v1`, with duplicate-key rejection and exact canonical-byte validation. The earlier JCS suggestion remains a future interoperability question; no JCS equivalence is claimed. It uses the safe unpacked directory and limits in the [normative profile](MODEL-BUNDLE-V1.md), and unsigned descriptive reviews remain outside the core digest.

## Executive recommendation

Design a **non-executable `ModelBundle-v1` package and offline validator** next, rather than an eighth KernelInput/KernelResult variant. Its closed, content-addressed *core* should bind exact source artifacts, legal-source descriptions, semantic-ID-to-byte-span mappings, the executable model artifact, and an enumerated positive scope with explicit exclusions. Keep review assertions **detached** and bound to the core digest. Start with unsigned, explicitly unauthenticated review records and a status such as `review_recorded_unverified`; do not call a model certified, authoritative or legally correct. The core's digest changes when any review-critical source, mapping, semantic item, scope or descriptive metadata changes, making an older review's subject digest non-matching. A mutable URL or catalog is a discovery aid, never the identity.

This adds a missing capability: a reviewer and consumer can identify the **exact bytes and exact modeled slice** to which a statement refers. The seven current kernel variants can validate local source hashes and spans, but cannot establish source publication, complete coverage, authenticated reviewer identity or temporal legal applicability. Packaging belongs at the compiler/build boundary, with a Haskell validator using the existing conservative validation approach; Python parsing may initially produce candidate artifacts through an explicit adapter. A stateless subprocess continues to accept the existing seven requests unchanged. Later integration may carry a separately versioned, prevalidated bundle reference *only if* its bytes or digest are verified at the process boundary. No accepted response bytes or Canonical IR v1.2 hash rules change. [Current architecture](YUHO-REWRITE-ARCHITECTURE-PROPOSAL.md), [criminal-outcome decision](CRIMINAL-OUTCOME-BOUNDARY-DECISION-REPORT.md).

These are architecture findings, not allegations that existing hash and span checks fail their stated purpose.

## Concepts that must stay separate

| Layer | Proposed v1 meaning |
| --- | --- |
| Source artifact | Exact stored bytes, media type, byte length and raw-byte SHA-256. |
| Manifestation | A particular PDF, HTML, XML, plain-text or other rendering. Several artifacts may manifest one expression; a downloaded file is one item/copy. |
| Expression/version | An asserted language, consolidation/revision or point-in-time wording of a work. Different expressions may share a work ID; identity claims require review. |
| Work/instrument | An abstract Act, subsidiary instrument, judgment or other work, not a byte stream. |
| Locator | URL or repository address for retrieval; it may change what it serves and is not content identity. |
| Source assertion | A person's or system's descriptive claim about publisher, jurisdiction, document type, dates, relationships or official status. It can be structurally checked, not accepted as authority by default. |
| Semantic mapping | Model-local semantic ID → exact artifact digest and valid byte span(s), with a role and cited provision/paragraph label. Multiple sources and mappings are allowed. |
| Model scope | Enumerated positive semantic IDs and source expressions/provision units, explicit omissions, dependencies, unsupported doctrines and review limitations. It is a statement about this model only. |
| Review assertion | A record claiming that a named reviewer considered an exact bundle digest and exact scope digest for a stated purpose, method and outcome. Presence is not authentication. |
| Authentication | A verified credential/signature-to-identity binding, absent from v1. |
| Trust policy | A consumer's separately configured rule for trusted publishers, credentials, reviewers, qualifications and freshness, absent from v1. |
| Applicability | A legally reviewed conclusion that a source governs a matter at a time/place; not inferred from dates in v1. |
| Correctness | An independently reviewed conclusion that the executable model faithfully represents the specified source and doctrine; not a hash property. |

**Scope is positive and exact.** A manifest lists every covered semantic ID with role (`definition`, `offence_element`, `exception`, `presumption`, `penalty_declaration`, `penalty_term`, etc.), every cited work/expression and provision/paragraph unit, and relevant dependencies. It also lists expressly excluded units and doctrines (general exceptions, cross-Act rules, procedure, sentencing, unmodeled provisions), plus a bounded free-text limitation. A canonical digest of the *sorted enumerated set* is useful for review binding, but the list remains in the artifact so humans can inspect it. Source ranges alone are insufficient: several legal rules may arise from one passage, and one rule may draw on several passages. Logical groups may be display aids, not substitutes for explicit IDs. A title such as “Penal Code model” cannot assert full-Act coverage; v1 has only `coverage_mode: "enumerated_only"`. An attempted `complete_instrument` claim is unsupported until completeness checks and legal review exist. Model source spans and complete semantic-ID inventory must match the manifest; an intentionally unmapped synthetic/internal ID needs an explicit `mapping_exemption` reason and cannot be presented as a source-backed legal rule.

For v1, pin SHA-256 and a single documented canonicalization profile; include `algorithm: "sha256"` so future versions can negotiate another algorithm **only by a new versioned profile**. No per-record algorithm roulette. Avoid normalizing Unicode, line endings or downloaded HTML/PDF bytes before artifact hashing. If extracted text is needed for spans, store it as a distinct UTF-8 artifact with its own digest, extraction-tool/version/parameters and a `derived_from` edge to the original manifestation. A reproducible transform checks extraction repeatability; fidelity of extracted wording remains review work.

The ELI 1.4 release note was readable through the source-rendering service, but direct HEAD access from this workstation returned HTTP 403 on 13 September 2026. The concepts above come from that rendered official document and the accessible ELI register, not from an assumed local download of its PDF bytes.

## Singapore source-system findings and limitations

[SSO's official About page](https://sso.agc.gov.sg/About-us) says AGC's Legislation Division manages SSO, which includes current and historical legislation, revised editions, Gazette as-published materials and repealed items; pre-1998 historical holdings are incomplete. [SSO FAQ B1–B10](https://sso.agc.gov.sg/FAQ) distinguishes the Government Gazette's published legislation from SSO's informal consolidation, directs users to the legislation timeline, says commencement depends on a Gazette notification, and notes consolidation can lag operation. The [SSO legislation/provision timeline guide](https://sso.agc.gov.sg/Help/SSO-Guide/Article/18/Document-Timeline-Provision-Timeline) separates document and individual-provision version timelines. **Implication:** register the as-published instrument, consolidation expression, provision identifier, amendment/commencement source and asserted date separately; do not derive operative law from retrieval time or a current URL. An SSO URL's syntax is a locator and possibly a useful asserted external ID, not a persistent raw-byte digest.

The Singapore Courts' [Types of Decisions](https://www.judiciary.gov.sg/judgments/judicial-decisions) describes judgments and neutral citations; the official [State Courts practice directions, Part IX](https://epd2021-statecourts.judiciary.gov.sg/part-ix-documents-and-authorities-for-use-in-court) describe a neutral citation as court-approved and unique to a written judgment, independent of reports. This identifies a judgment work/expression for citation, **not** its precedential force or the bytes of a PDF. An [eLitigation judgment PDF](https://www.elitigation.sg/gd/gd/2023_SGHC_227/pdf) explicitly says it is subject to final editorial corrections/redaction, illustrating why retrieval, manifestation and revision must be separately recorded. These materials were accessed 13 September 2026; this workstation's direct SSO link checks returned HTTP 403, while the cited eLitigation PDF returned HTTP 200. SSO page content was inspected through accessible rendered/indexed results; no captured case/Act bytes were authenticated or checked for completeness. No specific statutory provision is promoted to a fixture or declared applicable. A qualified reviewer must verify exact Singapore publication/version/commencement and cross-Act completeness for any concrete package.

Mechanically, a trusted fetcher *could* compare downloaded bytes to a pinned digest, parse a known page's version labels, validate dates/links and later compare an official signed distribution if one is specified. Yuho cannot mechanically conclude that a claimed Gazette issue, SSO page or neutral citation is authoritative merely from user-supplied bytes/URL. It also cannot infer omitted amendments, legal effective dates, precedential weight, semantic completeness or the legal meaning of an amendment.

## Provisional artifact hierarchy and lifecycle

The following names and constraints are proposals, not schemas. Every fixed object is closed; unknown/duplicate keys reject. IDs are unique **within one bundle**; external identifiers remain separately typed assertions. Arrays used as sets are sorted by a stated stable key for hashing; source-order arrays carry an explicit `declaration_index` and are never silently reordered.

| Object | Identity, content and references | Digest/placement |
| --- | --- | --- |
| `SourceArtifact` | `artifact_id`, media type, byte length, raw-byte `sha256`, relative safe path to stored bytes; optional `derived_from` artifact and pinned extraction recipe. Store each digest once; two locators may reference one artifact. UTF-8 text artifacts are distinct from source PDF/HTML. | Raw SHA-256 of **exact bytes**; blob store beside package, never fetched at evaluation. |
| `LegalSourceRecord` | Local work/expression/manifestation IDs, `artifact_id`, document kind, language, jurisdiction, external citation/identifier, locators and typed dated assertions (publisher, publication, enactment/decision, consolidation, effective-from/to, amendment/repeal/correction). Assertions carry issuer/source and verification state, not presumed authority. | Inside hashed bundle core; version-parent and artifact-derivation edges are acyclic, while amendment/correction relations are separately typed and may have paired inverse links. No mutable registry pointers. |
| `SemanticSourceMapping` | Semantic ID, role, source artifact ID and half-open UTF-8 byte span in a text artifact, optional cited provision/paragraph ID, mapping method and source-order index. Many-to-many; non-text origins go through a linked extracted-text artifact. | Inside hashed core, checked against model's complete semantic-ID inventory and span boundaries. |
| `ModelScopeManifest` | `coverage_mode: "enumerated_only"`, jurisdiction/subject/language, covered semantic IDs with roles and cited units, explicit exclusions, cross-source dependencies, unsupported doctrines, procedural/substantive classification, limitations and requested review purpose. | Inside hashed core; separate domain-separated `scope_digest` over its canonical bytes. No unqualified whole-Act claim. |
| Executable model artifact | Exact versioned model-input/template bytes and its digest; root and fragment/schema ID. A concrete request may supply facts/date separately; no legal source is implicitly refreshed. | Blob referenced in hashed core. Canonical IR v1.2 may be separately attached as migration evidence, not treated as executable model. |
| `ModelBundleCore` | Schema/version, canonicalization profile, references/digests to all preceding objects and blobs, declared build-tool identity/version and immutable package manifest. | `SHA256(ASCII("yuho.model-bundle/v1\0") || canonical_core_bytes)`; the digest field is outside hashed bytes. No review record points back inside core. Separately versioned from IR/kernel. |
| `ReviewAssertion` | `review_id`, exact bundle digest, scope digest, reviewed artifact digests/IDs, purpose, checklist version/method, outcome (`reviewed_with_limitations | changes_requested | unable_to_review`), limitations/exclusions, claimed reviewer ID/role/organisation, RFC 3339 timestamp, optional expiry/supersession and optional detached credential reference. | Detached append-only metadata, itself canonically hashed in a separate `yuho.review-assertion/v1\0` domain. Unsigned v1 only records a claim; it does not authenticate a reviewer. |

An **illustrative package shape**, deliberately separate from KernelInput v1, is:

```text
bundle/
  core.json                 # closed ModelBundleCore; no embedded digest or review assertion
  blobs/sha256/<hex>        # raw bytes, including a model registry/template artifact
  reviews/<review-id>.json  # detached claim whose subject is the core and scope digests
```

The proposed `core.json` fields are `schema: "yuho.model-bundle/v1"`, `canonical_profile`, `hash_algorithm: "sha256"`, `artifacts`, `legal_sources`, `semantic_mappings`, `scope`, and `model` (artifact digest, fragment name, root ID and semantic-ID inventory). `scope` carries `coverage_mode: "enumerated_only"`, `covered_semantic_ids`, `covered_source_units`, `excluded_source_units`, `dependencies`, `unsupported_doctrines` and `limitations`. A mapping is a closed tuple of `semantic_id`, `role`, `artifact_id`, `start_byte`, `end_byte`, and optional external unit identifier; it may repeat a semantic ID for additional supporting passages. A detached review names `subject_bundle_digest` and `subject_scope_digest`, not a mutable path. This is a **shape sketch**, not an accepted JSON schema; spellings, cardinalities and canonical array order need fixture review. There is no automatic rewrite of old requests: a packaging adapter materializes the existing KernelInput v1 source text/IDs from the pinned blobs and separately supplied case facts/date, then verifies that it used the registered artifact digests. The kernel still performs its own ordinary validation.

Compute `scope_digest` as `SHA256(ASCII("yuho.model-scope/v1\0") || canonical_scope_bytes)`. The core digest covers the scope bytes *and* every referenced artifact digest, source assertion and mapping. Review records stay outside that core so the subject cannot hash itself; altering a review creates a new review-record digest without changing the model. Core `source_id` mappings must be explicit and local; a publisher URL, neutral citation or external ontology IRI never silently becomes a semantic ID.

Suggested bounded profile for implementation review: package ≤64 MiB total, individual blob ≤16 MiB, ≤1,024 artifacts/source records, ≤8,192 mappings/semantic IDs, metadata JSON depth ≤64, mapping spans within existing UTF-8 byte/line rules. Reject compressed/archive traversal and symlinks outside the package. These **new** limits do not change the existing per-request kernel limits. Before adopting numbers, test legitimate reviewed multi-source examples and worst-case memory on the constrained host.

Provisional validation order: bounded byte intake → strict JSON/closed shapes/duplicate keys → canonical profile and object IDs → path containment, artifact existence and raw-byte digests → source-record references/typed chronology → extracted-text provenance and UTF-8 spans → complete model-ID enumeration and mappings → exact positive scope/exclusions/dependencies → compute bundle/scope digests → match detached review subjects → report trust state. Validation never invokes a URL or the rule evaluator. Cyclic derivation/metadata references reject; model semantic DAG validation remains the existing kernel's separate check. Unknown media types reject **as executable mapped text**; they may be stored as explicitly non-executable reference artifacts if the profile lists them. No partial negative rule result is returned on package rejection.

The build tool emits a deterministic directory/tar profile (stable paths, byte order, timestamps fixed or excluded, no ambient clocks in core). The validator works offline, then hands the unchanged seven-variant request to the subprocess. A service may cache `bundle_digest → validated package` only if it verifies digest equality on each load and invalidates changed bytes; a mutable catalog may locate packages but cannot substitute another digest. Initially CLI/LSP can show bundle/review state separately from kernel results. No automatic source update during evaluation.

## Temporal and trust boundaries

| Date | v1 origin/check | May it affect kernel applicability? |
| --- | --- | --- |
| Publication/Gazette date; enactment/decision date | Publisher or modeller **assertion**; validate calendar and cited source; human checks identity. | No. |
| Commencement, effective-from/to, repeal | Typed assertion with supporting amendment/notification relationship; check impossible/reversed dates and missing cited artifact. | No automatic date comparison or applicability inference. |
| Consolidation/revision date | Version expression metadata, distinct from commencement. | No. |
| Retrieval date | Fetch log, optionally an activity record; never a legal effective date. | No. |
| Model review date, expiry, supersession | Detached review metadata; UTC RFC 3339; structural ordering/freshness checks. | No. Consumer policy may mark a review stale. |
| Evaluation `reference_date` | Existing request policy date. | Existing kernel semantics only; not proof of point-in-time source selection. |

A valid digest establishes equality to the **recorded digest**. A local validator can claim `integrity_checked`, `scope_enumerated`, and `review_subject_matches_bundle` if those checks pass. It cannot claim publisher authenticity, legal authority/currentness, reviewer identity/qualification, source completeness, point-in-time applicability or model correctness. Unsigned reviews are `identity_unverified`. A future in-toto/DSSE envelope could establish that a credential signed a digest if verified; an external trust policy must still bind that credential to an authorized, qualified person and decide whether the review purpose covers this use. Conflicting reviews coexist and require policy/human resolution; the bundle never auto-selects the favorable one.

## Alternatives and provisional validation matrix

| Alternative | Judgment |
| --- | --- |
| A. All source/review bytes in every KernelInput | Self-contained but repeats large bytes, pressures request limits, mixes trusted build-time review with case facts and changes seven accepted wires. Reject as v1 native boundary. |
| B. Immutable content-addressed bundle | Offline repeatability, inspectable exact scope, stale-review detection, stateless process compatibility. **Recommend.** Updates create a new digest and must be reviewed anew. |
| C. External mutable source database | Useful as a discovery index only; mutable lookup and outages break determinism. Never trust an unpinned database result. |
| D. Native AKN/ELI/LegalRuleML/RDF | Rich interoperability but a large parser/ontology and jurisdiction adaptation surface; no automatic trust/legal correctness. Defer to import/export adapters. |
| E. Small closed Yuho JSON profile with adapters | Fits current Haskell protocol discipline and source IDs; define an exact mapping to standards later without mutating their meaning. Adopt within B. |

| Condition | Provisional v1 treatment |
| --- | --- |
| Duplicate local IDs, unknown/duplicate JSON keys, invalid paths, missing blob or semantic reference, digest mismatch, out-of-byte/invalid UTF-8 span, mapping to unregistered semantic ID, impossible local date ordering, cyclic typed metadata relation, size/count/depth overflow | Reject package as structural/integrity invariant or resource failure before evaluation; no legal negative result. |
| Executable semantic ID absent from mapping or positive scope | Reject unless a narrowly enumerated synthetic/internal exemption is present; an omitted *external* provision is recorded as excluded, never silently called covered. |
| Supported but partial coverage | Valid with `enumerated_only` scope and visible exclusions; **review incomplete** for any consumer demanding a larger scope. No global completeness claim. |
| Recognized unsupported hash algorithm, executable media type, unbounded external reference, signed-authentication/complete-instrument claim without implementation | Capability rejection for the claim; no fallback to weaker interpretation. |
| Conflicting publisher/version assertions, disputed effective dates, altered URL bytes, stale/expired or contradictory review | Preserve conflicting records; reject internally contradictory identifiers/digests, otherwise mark assertion untrusted or review stale and require external policy/legal resolution. Never invent semantic `unresolved`. |
| Unsigned review, claimed official URL, claimed reviewer qualification | Accept as clearly labelled **unverified assertion**, not trusted authority. |
| Offline URL unavailable | No runtime fetch or rejection if pinned bytes are present; unresolved external verification recorded for human/policy follow-up. |

The [threat model](MODEL-SCOPE-AND-PROVENANCE-THREAT-MODEL.md) gives a failure-by-failure disposition, including correct bytes attached to the wrong instrument and an authoritative source modeled incorrectly.

## Migration, gates and decisions

| Current behavior | Classification and migration rule |
| --- | --- |
| Existing seven request/result variants and exact bytes; source hash and span checks | **Preserved.** Bundle validates before they run; no eighth discriminator or IR v1.2 rehash. |
| Python parser and AST source locations; canonical IR source hash; existing fixture generators | **Adapter-only.** Export explicit raw/UTF-8 artifact bytes and map IDs/spans after checking parser/extraction version; never silently treat normalized text or IR snapshot as original source. Existing fixtures remain synthetic and unchanged. |
| Local `source_id`, source path, typed `source_label`, issuer label, jurisdiction/date | **Deliberately changed at package boundary:** retain as local/descriptive fields, map to typed source records when evidence exists, disclose conflicts and unmapped labels. Do not turn labels into global authority IDs. |
| Legacy PROV sidecars, source maps, corpus exports, CLI/LSP views | **Adapter-only/deferred.** Sidecars may seed extraction lineage, but ambient timestamps and approximate token maps are not signed reviews. UI should display actual scope and unverified trust state; source updates produce new packages. |
| Singapore offence/CPC vertical slices and cross-jurisdiction models | **Deferred.** Require explicit as-published/consolidation identities, cross-Act exclusions/dependencies and qualified point-in-time review before product claims. No corpus provision becomes authoritative merely by inclusion. |
| Implied whole-Act coverage, automatic source authority from URL/hash, automatic legal applicability from dates, automatically trusted reviewer | **Prohibited** in v1. |

Implementation gate: agree the exact object profile and digest test vectors (Unicode, duplicate keys, source-order arrays, large numbers), safe package limits, complete semantic-ID extraction for each of seven variants, PDF/HTML extraction policy, review-subject staleness tests, offline replay, adversarial path/digest/span tests and UI wording.
