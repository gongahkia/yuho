## Executive summary

**Repository change since the earlier handoff:** local HEAD is `8d0b8e6d71bb131f10cf20c6266282c20cdcc528` (`remotelykeepeverything`), one commit ahead of `origin/main`/the captured `b5f37d9e92ff11348836a273896c63185fc1b328`. `git diff --stat b5f37d9e..HEAD` shows only the addition of `YUHO_REPOSITORY_HANDOFF.md` (744 lines). No implementation, test, generated-parser, or CI configuration change occurred between those commits. The worktree was clean at the start of this audit.

The migration should **not** use the whole Python AST or Canonical IR v1.2 as an unquestioned replacement contract. The AST is broad, but the IR is partly a typed legal core and partly an opaque AST snapshot; execution still requires an AST adapter. The first replacement should be a small, pure semantic kernel behind an explicit versioned request/response protocol. Keep Python responsible for CLI, parser, exporters, corpus tooling and LSP during initial coexistence. Establish differential evidence before moving each boundary. No implementation language creates a proof merely by being functional.

Two related slices should be distinguished. A first *provable* fragment can cover named Boolean elements, recursive `all_of`/`any_of`, inherited subsection branches, and definition-only failure, excluding arbitrary expressions and external effects. A first *product-discriminating* vertical slice should add typed-fact metadata, simple exceptions, registered acyclic `is_infringed` guards, guarded sibling penalty selection and explicit unresolved traces. `tests/test_runtime_subsections.py`, `tests/test_runtime_exception_dependencies.py`, and `tests/test_runtime_penalties.py` provide concrete oracles. Penal Code s84 plus a CPC disposition is **not** current parity material: cross-Act packages and that CPC corpus are open issues #63/#66, while outcomes are only partially landed (#51).

## Proposed compatibility contract

### Preserve deliberately

1. **Source-language acceptance and rejection**, not just successful parses: `.yh`/`.yuho` UTF-8 input, comments/doc-comments, literal escaping, structs/types/functions, statutes and nested subsections, `all_of`/`any_of`, definitions/elements/exceptions/case law/penalties, imports/references, civil feature gating, and `#yuho v5.1`/`v5.1.0` pragma behavior. `Parser.validate_source` removes a BOM, rejects NUL and >10 MiB source; `parse_file` caps files at 10 MiB. The known typed-struct-literal ambiguity receives a fail-safe `Y0103`, not silent acceptance. Preserve diagnostics for malformed inputs, not Tree-sitter's internal CST shape as a public API.
2. **Observable semantic subset**, defined per feature rather than by the whole grammar: inherited ancestor requirements, sibling subsection alternatives, definition-only failure, Boolean/typed fact evaluation, same-fact cross-section dependencies, explicit unresolved results, trace paths, guarded penalties, and the supported limited case-effect semantics. The compatibility standard is intended behavior plus reviewed examples—not undocumented Python coercions or known legal encoding mistakes.
3. **CLI surface** from `src/yuho/cli/main.py`: `doctor`, `init`, `check`, `ci-report`, `upgrade`, `lint`, `fmt`, `ast`, `transpile`, `diff`, `test`, `verify`, `debug`, `explain`, `irac`, `literate`, `refs`, `schema`, `completion`. Options/aliases and stdin behavior are in `docs/user/cli-reference.md` and command modules. `yuho-lsp` is a second installed executable. `docs/user/cli-exit-codes.md` claims 0 success, 1 error, 2 warning, 130 interrupt, but this is **not universally implemented**: `run_check` returns 0 for warning-only JSON/SARIF and normal check, `run_lint` uses 2 for warning-only, and `run_verify` also uses 2 for unavailable/invalid prerequisites; Click usage errors normally use 2. Treat exact per-command behavior/tests as evidence and publish a corrected prospective contract before freezing it.
4. **Machine formats:** `AnalysisResult.validation_payload` phase validity/errors/warnings/lint/semantic/Canonical-IR summary; `AnalysisError.to_dict` with stage/message/`error_code`/location/node type; `ci-report` JSON `yuho-ci-report-v1`; SARIF 2.1.0 (`src/yuho/output/sarif.py`, rule IDs, `%SRCROOT%`, 1-based spans); JUnit XML for `test`; facts JSON primitive shorthand and `{ "facts": { name: {value,type,source,date,jurisdiction,evidential_status,burden,standard_of_proof,confidence} } }` (`src/yuho/eval/facts.py`, `docs/user/facts-schema.json`); AST JSON schema 1.0.0 (`src/yuho/transpile/json_schema.py`). 5. **Diagnostics:** analysis code families `Y0001`–`Y0007`, `Y0100`–`Y0103`, `Y0199`, `Y0200`, `Y0250`, `Y0300`, `Y0400`, `Y0499` in `src/yuho/services/analysis.py`; `YIR<CONSUMER>001` capability diagnostics in `ir/canonical.py`; `YRTP001` penalty conflict, `YROD001`–`YROD003` outcome, and `YRDG001`–`YRDG003` dependency-guard codes in evaluator modules; lint rule names/severity in `src/yuho/cli/commands/lint.py`; stage and source-location conventions. Preserve code/stage/severity/path semantics before human text.
6. **Exports:** registered JSON, English, LaTeX, Mermaid flow/mindmap, Alloy, DOCX, Akoma Ntoso XML, LegalRuleML; aliases/extensions in `src/yuho/transpile/base.py:TranspileTarget`; PDF and SVG/PNG are derived through external tools, not independent semantic backends. Snapshot fingerprints and source maps are existing compatibility signals, subject to intentional reviewed revisions. Source maps use version 3 (`src/yuho/transpile/source_map.py`); optional `.prov.json` sidecars use 1.0.0 (`src/yuho/provenance.py`) and include a current timestamp, so are not byte-deterministic.

Preserve protocol-visible behavior even if implementation changes. VS Code integration is under `editors/vscode-yuho/`.

Inputs are primarily CLI flags, `.yh`, and facts JSON; package/build configuration is `pyproject.toml`, `uv.lock`, `install.sh`, `src/tree-sitter-yuho/package*.json`, and `mechanisation/lean-toolchain`. ## Actual architecture and candidate semantic kernel

### Dependency and data flow

```text
source bytes/UTF-8
  -> parser/wrapper.py:Parser (tree_sitter + tree_sitter_yuho C grammar)
  -> tree-sitter CST, error/missing nodes and byte spans
  -> ast/builder.py:ASTBuilder -> ast/nodes.py immutable dataclasses
  -> services/analysis.py: lint + scope/type/jurisdiction checks + lower_module
  -> ir/canonical.py: CanonicalIR v1.2 / rule_branches
       -> eval/statute_evaluator.py: StatuteEvaluator + AST adapter
          -> eval/interpreter.py expressions, eval/defeasible.py guards,
             eval/facts.py fact conversion, eval/outcomes.py results
          -> explain/datalog.py -> English/IRAC/CLI traces
       -> verify/z3_solver.py (in-process z3 + AST adapter)
       -> verify/alloy.py (AST adapter -> .als -> Java subprocess)
       -> transpile/* (predominantly AST visitors, source maps)
  -> CLI commands, LSP, corpus and release scripts
```

Import direction is not a clean layered DAG: `ast/*` analyses depend on `ast/nodes.py`; `parser/wrapper.py` depends only on location and the native package; `services/analysis.py` imports parser, AST, lint and IR; `ir/canonical.py` imports AST; `eval/*` imports AST, IR and each other; `verify/*` imports AST/IR; `transpile/*` imports AST and often other exporters; CLI/LSP import most layers. `yuho/ast/__init__.py`, `yuho/eval/__init__.py`, `yuho/transpile/__init__.py`, and `yuho/verify/__init__.py` re-export many modules; lazy imports in `TranspilerRegistry._register_builtins`, `DefeasibleReasoner`, and fact helpers avoid or defer coupling. There is no evidenced SQLite runtime dependency: analysis persistence is bounded JSON files (`services/safe_cache.py`).

The current oversize translation units are `verify/z3_solver.py` (2,353 lines), `ast/builder.py` (1,900), `eval/statute_evaluator.py` (1,753), `ast/nodes.py` (1,608), `eval/interpreter.py` (1,103), and `services/analysis.py` (1,095). Global/stateful seams include the locked module parser singleton (`parser/wrapper.py:get_parser`), `TranspilerRegistry` singleton plus custom factories/instance cache, `Environment`'s mutable bindings/statute registry, interpreter state, LSP per-URI caches, and optional on-disk analysis cache. `services/analysis.py:_cache_type_allowlist` uses reflection over dataclass/enum module members; visitors and exporters use `getattr`/`hasattr` fallbacks; `ASTNode.accept` is dynamic visitor dispatch. `ReturnSignal` is exception-based control flow in `eval/interpreter.py`; parser/analysis and CLI use exception boundaries and `sys.exit`. No general monkey-patching/plugin entry-point loader was found in production, but tests use `monkeypatch`, and custom transpiler registration is an extension point. A future pure core should take registry, facts, date, and feature policy as explicit inputs, not inherit ambient Python state.

Pure or almost-pure candidates: typed AST-to-IR lowering, branch enumeration, Boolean requirement evaluation, typed fact metadata comparison, deterministic serialization, capability checks, diagnosis normalization, and bounded penalty selection. Effectful boundaries: source I/O/import resolution, incremental parser state, cache, watch/LSP, user CLI output, Z3 native state, Alloy/Java/Lean subprocesses, rendering, XML validation, Git/provenance timestamps, scraping/network, packaging.

### Narrowest coherent first rewrite

Define a separately versioned `KernelInput` containing one *validated*, closed statute graph (named elements, `All`/`Any`, provision paths, optional simple exception guards and explicit registered references), normalized facts, and deterministic policy. Define `KernelResult` as branch/evidence statuses (`true | false | unresolved`), element traces, selected penalty source IDs, outcome state, and typed diagnostics. Let Python perform CST/AST construction and projection into that request. The new implementation must validate request invariants itself and emit canonical JSON; Python remains a thin caller, not a semantic fallback. Begin with Boolean branches only, then extend one construct at a time. This is narrower than moving all AST classes, exporters or corpus scripts, yet rich enough to test real legal-rule composition.

`CanonicalIR` v1.2 is **not yet a sufficient wire format** for this kernel: `CanonicalElement.description` can be an opaque `CanonicalNode`, penalties/exceptions are snapshots, `CanonicalOutcomeTransition` stores string kind/target but not executable guards, and source spans are dropped. `StatuteEvaluator.evaluate_canonical(..., ast_adapter=...)` literally requires a `StatuteNode`. First specify a v1.3 (or independently named kernel-input v1) closed typed subset with source IDs/spans and explicit unsupported cases. Do not silently reinterpret v1.2 hashes; version and golden-test the repaired representation. Preserve v1.2 read/compare support during migration where practical.

## Parser and domain-model audit

`Parser._ensure_initialized` loads the Python `tree_sitter` API and the `tree_sitter_yuho` C-language binding built by `src/hatch_build.py`. `Parser.parse` normalizes a grammar pragma by rewriting its two leading characters to `//`, passes UTF-8 bytes to Tree-sitter, collects ERROR/MISSING nodes and feature errors, and returns a tree plus original source. `_compute_tree_edit` computes UTF-8 byte positions; `parse_incremental` edits a prior tree. `SourceLocation.from_tree_sitter_node` turns zero-based Tree-sitter byte columns into one-based displayed columns and retains byte offsets. `ASTBuilder` slices UTF-8 source bytes and attaches locations; it extracts `///` doc-comments via CST children or adjacent lines. Other comments are extras/trivia, not losslessly represented in AST/IR. `Parser._collect_errors` slices a Python string using Tree-sitter byte offsets, so non-ASCII error snippets may be inaccurate; a rewrite should test this rather than mimic it.

`grammar.js` declares five external tokens (`_string_content_external`, interpolation start/end, `_error_sentinel`, typed-struct-literal type name), whitespace/ordinary comments as extras, `identifier` as `word`, 11 conflict declarations, seven inlined syntactic categories, lexical/grammar precedence and `token.immediate` for strings/percent. `src/scanner.c` keeps string/interpolation state and performs lookahead for typed struct literals. The grammar also has literals, doc comments, nested provisions, expressions, types, and feature-gated civil forms. Generation is local `npm ci` then `tree-sitter generate`; `scripts/verify_generated_grammar.py` verifies in a temporary copy, but this must not be run on the resource-constrained workstation without checking load. Known defect #39 is the non-doc-comment-before-typed-struct-literal split, guarded by `Y0103`; outcome rules are absent from generated `parser.c`/`node-types.json` despite being in grammar source and `grammar.json`.

**Parser strategy:** a batch parser using Happy/Alex or Megaparsec in Haskell, or Menhir/Sedlex or Angstrom in OCaml, *could* serve the compiler. Tree-sitter is not theoretically required for statute semantics. But the current compiler's `ASTBuilder` consumes Tree-sitter node types/fields/byte spans, and LSP uses error recovery and incremental trees. Replacing it requires a new AST constructor, differential tests, diagnostics, comment/source-span policy, and editor split. Keeping Tree-sitter for the editor while using a separate batch grammar is feasible but creates two acceptance languages unless a shared conformance suite gates both. The lowest-risk first phase is to retain Tree-sitter through C FFI or a Python parser subprocess and migrate behind AST/IR. Lossless CST is **not** currently a semantic requirement; comment retention matters for doc-comment/fidelity and formatter behavior; exact source mapping, error recovery and incremental parsing are hard *workflow* requirements for CLI/LSP parity, even if delivered by separate components.

AST type graph (`ast/nodes.py`): `ModuleNode` owns imports, type/enum/alias/function definitions, statutes, variables, facts and assertions; `StatuteNode` owns definitions, recursive `ElementGroupNode`/`ElementNode` or civil primitives, penalties, exceptions, outcomes, case law, nested `SubsectionNode`, parties, temporal constraints and annotations. `ElementNode` has string `element_type`, AST description, `caused_by`, actor/patient/agent and burden metadata. `PenaltyNode` has optional imprisonment/fine/caning/death axes, sentinel flags, combinator, condition, nested penalty and mandatory minima. `ExceptionNode` has string condition/effect, optional AST guard/typed outcome, priority and defeat relation; `CaseLawNode` has treatment, precedence and fact-effect metadata. `PartyNode`, `FactEventNode` and `TemporalConstraintNode` exist. `OutcomeNode` has string kind/target/guard. All inherit optional `SourceLocation`; dataclasses are frozen, but nested dict fields and some result types are mutable.

IR graph (`ir/canonical.py`): `CanonicalIR(schema,version,module,source_hash)` -> `CanonicalModule(statutes,snapshot)` -> `CanonicalStatute(root)` -> recursive `CanonicalProvision(definitions,elements,penalties,exceptions,outcomes,dependencies,children,metadata)` -> `CanonicalRequirement = CanonicalElement | CanonicalElementGroup | CanonicalNode`. `rule_branches` creates inherited path leaves with `CanonicalSourceNode` references; `CanonicalDependency` records explicit section edges and `CanonicalOutcomeTransition` stores source-local kinds/targets. `CanonicalNode` snapshots all other dataclasses and nested mappings. The new typed representation should make impossible: unknown element/group/outcome strings; empty `Any` if legally unintended; invalid source/declaration references; duplicate section IDs; unresolved target encoded as a valid target; penalty min>max/currency mismatch/sentinel-plus-finite-max; cycles in a supposedly closed dependency DAG; proof-state and Boolean truth conflation; conflicting `defeats`/`defeat_relation` fields; typed outcome target missing for `reduce_to`/`disposition`; missing provenance for a purportedly reviewed rule. Plain algebraic data types plus smart constructors are enough for most of this. GADTs/phantom types or OCaml module abstraction are justified only if phase-indexing (`Parsed`/`Resolved`/`Executable`) or typed expressions actually removes broad runtime checks; existential packaging is useful only for heterogeneous typed values in one fact map. Avoid advanced type machinery for statute tags, issue codes and recursive rule trees where ordinary ADTs are clearer. Neither Haskell nor OCaml types prove legal fidelity or terminate arbitrary cross-reference graphs without explicit invariants/proofs.

## Operational semantics and discriminating examples

For each statute, `rule_branches(lower_statute(...))` walks the provision tree. A child inherits ancestor requirements, penalties, exceptions, outcomes and dependency edges; sibling element-bearing leaves are alternatives. A provision with executable descendants does not itself become a leaf; a provision with no executable element-bearing path yields `definition_only`, `overall_satisfied=False`. Within a path, direct requirements are conjunctive, recursive `all_of` and `any_of` use Boolean `all`/`any`, and element descriptions are interpreted through the AST adapter and `Interpreter`. Fact lookup first tries an exact key then a normalized-name scan (`StatuteEvaluator._matching_fact_value`), which can be order-dependent on colliding normalized keys. Primitive facts retain Python truthiness; typed fact `value` determines truth, and supplied burden/standard metadata must match a declaration when both are present. Missing/false elements yield false, not a complete epistemic `unknown` state.

Exceptions are evaluated only on a satisfied branch. The reasoner evaluates guards with the caller's `Environment` and statute registry; explicit `is_infringed` edges are traced. A missing target, cycle, unsupported override or guard diagnostic yields branch `None` (unresolved). A true guard—or a legacy exception-key truthy fact—defeats the branch, then attaches a typed transition or `legacy_acquit`; a false guard leaves it true. The first firing exception returns early, so exception declaration order matters in conflict cases. Branch aggregation is true if any branch true, else unresolved if any unresolved, else false. `EvaluationResult.overall_satisfied: Optional[bool]` is a compatibility projection, not a general three-valued logic over every element.

Penalties are selected only from satisfied branches. Guards match evaluated element names, then fact keys, then environment values; unguarded and same-guard blocks accumulate. Distinct simultaneously true sibling guards retain every candidate and emit `YRTP001`, rather than choose one. Selection is source-index sorted and records branch paths. A `CriminalOutcome` is then resolved: ordinary true -> `convicted`; false -> `not_proved`; unresolved -> `unresolved`; firing exception -> `acquitted`, `reduced_to` or special disposition where supported. Reduction recursively evaluates a named target in the active registry; missing/unresolved targets produce diagnostics. This outcome path is new and incompletely integrated. Case-law effects are chosen by jurisdiction/court/doctrine/date and declaration index; compatible non-conflicting effects apply in declaration order. `Environment`, fact normalization, precedence tie-breakers, and current-date-sensitive duration comparisons must be explicit in a replacement.

Cross-implementation golden cases should include: empty-fact failure for s84 and s511 (`tests/test_runtime_subsections.py`); a synthetic root `all_of` plus two nested alternative leaves, each with positive/negative facts; same-fact `is_infringed` success, missing target, cycle and fact override rejection (`tests/test_runtime_exception_dependencies.py`); s304A rash-only, negligent-only, both-guard conflict and neither (`tests/test_runtime_penalties.py`); typed versus primitive burden mismatch (`tests/test_burden_runtime.py`); currency rounding and calendar-duration reference-date cases (`tests/test_core_units.py`); case-effect precedence/treatment cases (`tests/test_case_law_effects.py`); definition-only no-vacuous-conviction; a parser-accepted but backend-unsupported feature; and an outcome fixture explicitly marked experimental until #51 is complete. For legal correctness, add independently reviewed expected doctrine rather than just Python outputs; s299 and ss302/304 are known counterexamples to blind Python parity (#52/#53).

## Formal-assurance boundary

Lean's core is **handwritten**, not extracted production code. `Yuho/AST.lean` defines `ElementKind`, `Element`, recursive `ElementGroup`, opaque `Guard = (String -> Bool) -> Bool`, `Exception`, `Statute`, `Module`; `Facts.lean` defines Boolean facts and optional typed burden metadata; `Eval.lean` defines element/group evaluation, exception firing and `Statute.convicts`. `Graph.lean` relates group evaluation to abstract per-group SMT atoms. `Cross.lean` and `CrossDeep.lean` model qualified cross-section atoms, finite lookups, `applyScope` and fuel-bounded deep calls. `Penalty.lean` proves bounded footprint admissibility for an abstract penalty algebra. `CaseLaw.lean` models a bounded effect/treatment/precedence subset. `Generator.lean` constructs abstract SMT formulas/models and proves correspondence for its own structures. None consumes production Canonical IR v1.2; `ir/canonical.py` explicitly marks Lean unsupported. In particular, Lean's top-level `Statute` omits production subsections, outcome transitions, provenance, arbitrary expressions and result traces; the corpus fixture generator **flattens** subsection elements and replaces exception guards with placeholder fact atoms (`mechanisation/scripts/generate_fixtures.py`). This is a material semantic gap, not a mere missing build step.

Python generates `mechanisation/scripts/Fixtures.lean` from `.yh` ASTs. Lean's `ExportSpec.lean` emits formula/verdict/footprint JSON. `scripts/verify_structural_diff.py` compares normalized Lean formula shape to Python `Z3Generator`; `verify_lean_expected_verdicts.py` compares Lean expected rows with runtime/Z3; `verify_lean_penalty_footprints.py` compares penalty rows. The trusted computing base includes Lean kernel/stdlib axioms, fixture selection/generation, Python AST and Z3 encoder, shape normalization, and the assumption that these abstractions correspond to production rules. The existing Lean README reports prior builds, but no current local Lean build was run. Solver agreement is not certified proof reconstruction.

The smallest realistic named claim is **`ClosedBooleanBranches-v1`**: a closed, unique-section/element, finite recursive `All`/`Any` tree with inherited subsection paths, total Boolean fact map, no arbitrary AST expressions, no exceptions/outcomes/penalties/external dependencies, and an explicit definition-only rule. Define a Lean reference evaluator of exactly this IR and test parsed projection/new-kernel output against language-neutral canonical fixtures; then prove the new kernel corresponds to that reference *if* a formal semantics/implementation link is supplied. Extend later to `AcyclicGuardedExceptions-v1` after target resolution, unresolved behavior and exception order are specified. Four assurance levels must remain separate: (1) host-language type safety/smart-constructor validation; (2) property and Python-vs-new differential tests; (3) Z3 agreement on an explicitly shared subset; (4) kernel-checked Lean theorem about a named model and, only with a proven bridge, implementation refinement. Language-neutral canonical fixtures plus a small Lean reference interpreter are the least disruptive preservation path. Generated Lean terms may help once the IR subset is closed; extraction/rewrite is premature while production semantics and parser projection are still changing.

Capture parse/AST/IR projection separately from evaluation. Compare schema-validated result JSON for status, branches, element results, dependencies, outcomes, selected penalty IDs, ordered diagnostics and source paths; compare exports by reviewed target-specific golden files. ## Migration topology and retirement gates

| Coexistence boundary | Strength | Cost/risk | Exit path |
|---|---|---|---|
| **Versioned subprocess JSON** (recommended initially) | Language-neutral, crash/memory isolation, record/replay fixtures, easiest differential testing and eventual Python deletion | Serialization/launch overhead; must version errors and source spans; keep request bounded | New CLI/LSP/exporters can later call same executable directly or move natively. |
| Shared C ABI | Low overhead and direct Tree-sitter interop; viable for editor parse hot path | Lifetime/allocator/exception/ABI mismatch and hard crash debugging, especially for OCaml/Haskell runtimes | Feasible for a narrow parser shim, poor first semantic boundary. |
| Direct Python embedding or extension | Fastest reuse of existing Python callers | Hidden GIL/runtime state, deployment complexity, memory coupling and Python deletion becomes harder | Treat as temporary adapter only, never the authoritative semantics. |

First five uncertainty-reducing milestones:

1. Publish a feature/status/compatibility manifest: accepted syntax versus executable versus Z3/Alloy/Lean versus legally reviewed; freeze one canonical fixture schema and semantic hash policy. Resolve whether v1.2 needs a v1.3 closed subset.
2. Build a small parser/AST/IR differential corpus including non-ASCII spans, comments, malformed recovery, #39 ambiguity, nested sections and outcome syntax; decide Tree-sitter FFI versus editor-only use with measured effort.
3. Implement the closed Boolean branch kernel in *both candidate prototypes* behind the same subprocess JSON, and compare precise traces plus memory/latency on small fixtures. This tests Haskell/OCaml fit without porting volume.
4. Add typed facts, simple exceptions, registered acyclic dependencies and guarded penalties one at a time; require reviewed counterexamples and unsupported diagnostics. Bring Lean reference fixtures into this subset.
5. Run serial cross-implementation conformance over representative corpus strata, then one 524-section non-executing parse/lower sweep in CI or a resource-safe host. Define release packaging/protocol promotion and an explicit Python retirement checklist.

Retire Python parser only after grammar acceptance/error-recovery/incremental/editor/source-map oracle passes, generated artifacts align and `.yh` corpus parse coverage holds. Retire AST/analysis only after all currently supported diagnostics, imports/types/lint, serializations and cache invalidation have replacements. Retire runtime only after full supported-fragment differential plus independently reviewed doctrinal cases and unresolved/outcome semantics. Retire Z3/Alloy after capability-rejection and solver-differential gates. Retire exporters after reviewed snapshots, source maps, schema/XSD and document rendering gates. Retire CLI/LSP after command/exit/JSON/SARIF/JUnit/protocol/editor tests. Retire corpus tools/release scripts after provenance, scraping/rebuild, distribution and audit gates. Delete Python last, when all required workflows have new owners, not when merely the kernel compiles.

Delay irreversible decisions about implementation language, parser replacement, public IR schema, source-spans encoding, a plugin ABI, typed expression sophistication, solver FFI, package manager/distribution, and deletion of Python until the small probes and evidence gates above distinguish them.
