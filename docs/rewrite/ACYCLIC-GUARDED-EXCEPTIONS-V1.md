# AcyclicGuardedExceptions-v1

**Status:** Normative technical semantics for the bounded Haskell kernel fragment, 12 September 2026. This is not a legal-doctrine finding or a proof of implementation correspondence. The [accepted Haskell ADR](ADR-0001-HASKELL.md) selects the implementation language; proof-tool selection remains open.

## Scope and wire shape

This fragment extends `yuho.kernel-input/v1` and `yuho.kernel-result/v1` under `yuho.kernel-protocol/v1`. The fragment discriminator is exactly `AcyclicGuardedExceptions-v1`. It reuses the closed provision, recursive `leaf`/`all`/`any` requirement, total Boolean fact and policy shapes from `ClosedBooleanBranches-v1`. It adds no syntax parser or change to Canonical IR v1.2. The [production request schema](../../rewrite/haskell/schema/request.schema.json) and [result schema](../../rewrite/haskell/schema/result.schema.json) express the two closed fragment variants; the Haskell decoder additionally enforces semantic invariants.

An evaluate request contains `protocol`, `request_id`, `operation`, `input_schema`, `fragment`, `sources`, `policy`, `registry`, `root_rule` and `facts`. Each named source contains `id`, relative POSIX `path`, `text` and UTF-8 `sha256`. Each rule contains a qualified `id` of the form `namespace:local`, `source_id`, a provision `program`, and ordered `exceptions`. Each exception contains `id`, `branch_id`, `source_id`, `span`, `guard` and `effect`. The only guard is `{ "kind": "is_infringed", "target": "namespace:local" }`; the only effect is `"defeat"`. `branch_id` names an executable branch of its containing rule. Source and exception IDs are explicit. Fact maps and diagnostic parameter maps alone have dynamic keys. The policy contains a real `YYYY-MM-DD` Gregorian `reference_date` and `max_nodes` from 1 to 1024.

The request has one root rule and a finite closed registry. Rule and source IDs must be qualified. Every source, rule, provision, requirement and exception ID is nonempty and globally unique in this fragment. Every target resolves to exactly one registered rule, including targets in rules the root cannot reach. Every rule and exception source resolves to its named source; an exception uses its containing rule's source. Exception spans must lie within their branch spans. Every source span uses zero-based, half-open UTF-8 byte offsets and one-based byte line/columns, agrees with the supplied source bytes and lies within its source. The supplied facts are total over every leaf in the complete registry and contain no extra leaf names. Empty registries, invalid provision/requirement shapes, unmarked nonexecutable rules, unknown fields and duplicate JSON keys reject. The whole registry must be acyclic, including unreachable subgraphs. JSON depth is at most 64 containers and a request line at most 1,048,576 bytes before the line terminator. IDs are counted against `max_nodes` before recursive domain decoding and checked after construction.

There is no fact override, target-specific context, priority, first-match control, arbitrary expression, callable guard, mutable registry or ambient clock. The target receives exactly the same total fact map, reference date and deterministic policy as its caller. The validated graph stores these shared values once. Current Boolean rules do not inspect the date, but the date is still validated and transported as part of the shared context. These are technical fragment limits; typed facts, burdens, penalties, outcomes, dispositions, case-law effects, CPC packages, section 84 doctrine, Z3 and source-language changes require later versioned work.

## Evaluation and aggregation

Validate the entire input and resolve all target names before any judgment. Evaluate ordinary requirements and inherited ancestor requirements exactly as in `ClosedBooleanBranches-v1`. Only a branch whose ordinary requirements are true evaluates its attached exception guards. A false ordinary branch has reason `requirements_failed`, no exception observations, and status false. For a satisfied branch, evaluate **every** attached exception in declaration order, including guards after a true one. Each guard evaluates the target's overall rule status: target true gives guard true; target false, including a target defeated by its own exception, gives guard false; target unresolved gives guard unresolved. A true guard defeats only its containing branch. Every true guard is applicable and appears in the result; no guard has priority.

| Guards on a satisfied branch | Branch status | Reason | Applicable exceptions |
|---|---|---|---|
| No guards, or all false | true | `satisfied` | none |
| One or more true, with any false or unresolved | false | `defeated` | **all** true guards |
| No true, at least one unresolved | unresolved | `guard_unresolved` | none |

True dominates unresolved only for the branch verdict. Unresolved guard observations and their target dependency edges remain in the trace as non-controlling information. Overall rule aggregation is true if any executable branch is true; otherwise unresolved if any is unresolved; otherwise false. A defeated branch plus a satisfied alternative therefore yields true, while all alternatives defeated yields false. Definition-only behavior remains false with no executable branch, as in the first fragment. A defeat is distinct from failed ordinary requirements.

With total Boolean facts, a completely valid closed DAG, and only the supported guard, a wire request currently produces true or false, not unresolved. The three-valued guard and branch aggregation functions nevertheless define unresolved behavior and are exercised at a pure internal boundary. Missing targets and cycles cannot be used to manufacture a legal unresolved judgment; they reject before evaluation. A future uncertainty source requires a new reviewed input extension.

## Result, trace and order

The exception-discriminated result envelope contains `protocol`, `request_id`, `result_schema`, `fragment`, `input_digest`, `root_rule`, `status`, `rules` and `diagnostics`. Each evaluated rule gives `id`, `source_id`, `status`, `provision_kind`, ordered `branches` and ordinary requirement `trace`. Each branch gives `id`, `path`, `status`, `reason`, ordered `trace_ids`, ordered `exceptions` and ordered `applicable_exceptions`. Each exception observation gives `id`, `source_id`, `span`, `target_rule`, `target_status`, `guard_status` and `applicable`. Its containing rule/branch and target fields form an explicit dependency edge. The target rule's own result retains the nested dependency trace. A shared diamond target is listed once among evaluated rules; every referencing exception edge is still emitted.

Rule results follow registry declaration order, limited to rules actually evaluated. Branches follow provision source order; requirements and ordinary trace edges retain their established order. Exception observations and applicable IDs follow exception declaration order. That order affects presentation and trace equality, never verdict or the set of applicable IDs. JSON object keys are sorted by the explicit canonical encoder; arrays are not sorted. Repeated identical requests produce identical response bytes. Rejections after fragment dispatch have `status=rejected`, an empty rule list and ordered typed diagnostics. A malformed JSON line or overlong line cannot be dispatched by fragment and retains the existing Boolean-shaped transport rejection envelope (`status=rejected`, empty branches/trace); it is not a Boolean legal judgment. The old Boolean result variant and its exact golden bytes are unchanged.

Diagnostic classes remain separate: `KPROT001` is protocol-version failure; `KDEC001/002` cover malformed JSON, shape and wire limits; `KINV001–006` cover fact totality, duplicate IDs, invalid spans, other model invariants, missing references and cycles; `KCAP001` rejects unsupported constructors, effects or fragment operations; `KERR001` denotes an internal evaluation inconsistency. Unknown closed-object fields are invariant failures. Missing or ambiguous targets and cycles are model invariant failures. Unsupported guards are capability rejections. None becomes `false` or `unresolved`.

## Examples, migration and assurance

The synthetic [E02 request](../../rewrite/haskell/test/exception-fixtures/requests/E02.json) has true caller requirements and a true registered target; the root branch is `false` with reason `defeated` and the exception is applicable. [E04](../../rewrite/haskell/test/exception-fixtures/requests/E04.json) has two true targets and reports both. [E18](../../rewrite/haskell/test/exception-fixtures/requests/E18.json) reverses the two exceptions from E17; the trace order changes, while the verdict and applicable-ID set do not. [E14](../../rewrite/haskell/test/exception-fixtures/requests/E14.json) fails ordinary requirements, so it never evaluates its registered target. [E09](../../rewrite/haskell/test/exception-fixtures/requests/E09.json) and [E11](../../rewrite/haskell/test/exception-fixtures/requests/E11.json) are counterexamples to treating missing targets or cycles as uncertainty: both reject as model invalid. The [fixture manifest](../../rewrite/haskell/test/exception-fixtures/MANIFEST.json) and [proof-neutral vectors](../../rewrite/haskell/test/exception-fixtures/PROOF-VECTORS.json) cover the full reviewed synthetic set.

The legacy Python runtime may return after the first firing exception, let declaration order select the controlling exception, or report missing/cyclic/unsupported dependencies as unresolved. Those observations are migration evidence, not the production rule here. Every guard is evaluated and every true exception reported; declaration order is presentational; missing targets and cycles invalidate the model; unsupported guards receive capability rejection. These choices are not universally correct legal doctrines. Any doctrine-specific priority or defeat relation needs a new versioned fragment and legal review.

The proposed future proof relation compares a validated Haskell graph with a proof-neutral reference graph preserving rule/exception IDs, dependency edges, branch paths, facts, policy date, statuses, fired sets and trace order. For each well-formed graph and total fact map, the intended relation equates branch/rule judgments and ordered essential traces. The present evidence is limited to Haskell types and constructors, validation and bounded property tests, synthetic fixture agreement, and proof-neutral vectors. No theorem prover was run; there is no claimed refinement proof, full-backend parity or verified legal correctness. The production language does not select Lean, Rocq or F*.
